# SEUT Simulation Platform — API

> **Note:** The frontend lives in a separate repository (`ssp-web`). The web container proxies `/api/*` to this service.

Python REST API for a facilitator-led classroom simulation platform. Handles session lifecycle, participant management, sprint progression, response submission, scoring, and scenario administration.

## Tech Stack

- **Python 3.11+** with Flask (WSGI via Gunicorn)
- **SQLite** for persistent storage (file-based, zero-config)
- **DynamoDB** optional backend (for AWS deployment)
- **pytest + Hypothesis** for unit and property-based testing

## Getting Started

### Prerequisites

- Python 3.11+

### Install

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### Local Development

```bash
source .venv/bin/activate
python local_server.py
```

Runs on `http://localhost:8000`. No Docker or Flask required — uses a standalone HTTP server with full route support.

### Docker

```bash
# Create the shared network (one-time)
docker network create ssp

# Build and run
docker compose up --build
```

The Compose service is deliberately named `api`, establishing the default Docker DNS endpoint `api:8000` on the shared `ssp` network. The web container (from `ssp-web`) uses that value as its default `API_UPSTREAM`.

Docker-network and host access are independent: containers use the service name and container port (`api:8000`), while a `ports` mapping controls direct host access. For example, `8051:8000` publishes the same API at `http://localhost:8051` without changing the web container's upstream.

### Running Tests

```bash
source .venv/bin/activate
pytest tests/
```

Or without activating:

```bash
.venv/bin/python -m pytest tests/
```

## Architecture

### Current: Docker + Gunicorn

The API runs as a Flask/Gunicorn WSGI app inside a Docker container. The web frontend's nginx reverse-proxies `/api/*` to this service over a shared Docker network.

```
┌─────────────────┐         ┌─────────────────┐
│  ssp-web        │         │  ssp-api        │
│  (nginx)        │────────▶│  (gunicorn)     │
│  port 3000      │  /api/* │  port 8000      │
└─────────────────┘         └────────┬────────┘
                                     │
                            ┌────────▼────────┐
                            │  SQLite         │
                            │  sessions.db    │
                            └─────────────────┘
```

### Target: AWS Serverless

The destination architecture is API Gateway + Lambda, with the service layer invoked directly by Lambda handlers (no Flask/Gunicorn):

```
┌─────────────────┐         ┌─────────────────┐
│  CloudFront     │         │  API Gateway    │
│  + S3 (SPA)     │────────▶│  REST routes    │
└─────────────────┘         └────────┬────────┘
                                     │
                            ┌────────▼────────┐
                            │  Lambda         │
                            │  handlers/      │
                            └────────┬────────┘
                                     │
                            ┌────────▼────────┐
                            │  DynamoDB       │
                            └─────────────────┘
```

- The `handlers/` directory already contains Lambda-compatible wrappers that delegate to `src/service.py`.
- `src/repository_factory.py` selects the storage backend (`sqlite` or `dynamodb`) based on the `STORAGE_BACKEND` env var.
- When deployed to Lambda, `wsgi.py` becomes obsolete — API Gateway handles routing and CORS.
- DynamoDB replaces SQLite as the persistent store (see `src/dynamo_repository.py`).

The codebase is structured so both architectures work today: Docker/Gunicorn for local dev and staging, Lambda-ready handlers for AWS deployment.
